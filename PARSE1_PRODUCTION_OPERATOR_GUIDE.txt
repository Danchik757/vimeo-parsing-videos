PARSE-1 PRODUCTION OPERATOR GUIDE
================================

This file describes the current production run setup for parse-1 on the server.
It is written for the actual queue-based launcher and offload watcher now used in
the repository.


1. WHAT IS RUNNING
------------------

Production parser command:

  cd /29d_kon/projects/vimeo-parsing-videos
  source venv/bin/activate
  python run_assigned_shards.py \
    --config config.parse-1.profile.json \
    --manifest data_shards/server_assignments_10000/parse-1/manifest.json \
    --workers 8

Offload watcher command:

  cd /29d_kon/projects/vimeo-parsing-videos
  source venv/bin/activate
  python scripts/offload_downloads.py --config config.parse-1.profile.json --watch --delete-local-video

Current production intent:

- server label: parse-1
- worker slots: 8
- authenticated Vimeo session: enabled
- only Original videos are downloaded
- media download goes directly through telegram-wg
- completed downloaded videos are offloaded to mimas
- local media file is deleted after verified upload


2. WHAT EXACTLY THE PARSER DOES
-------------------------------

Input source:

- config.parse-1.profile.json points to need_parse_unique.json as the master URL source
- the queue runner actually uses:
  data_shards/server_assignments_10000/parse-1/manifest.json

Manifest scope:

- parse-1 has 24 shard files
- each shard is usually 10000 URLs
- total for parse-1 is about 240000 URLs

Queue behavior:

- there are 8 worker slots, not 8 fixed worker lists
- at start, slots pick batches 0001..0008
- when a slot finishes its current batch, it picks the next pending batch
- a fast slot may process more batches than a slow one
- this is better than fixed assignment because heavy Original batches do not leave
  fast workers idle

Important difference from run_workers.py:

- run_workers.py splits one input list once and every worker stays on its fixed shard
- run_assigned_shards.py keeps a dynamic queue of batch files and reuses freed slots


3. CURRENT PARSE-1 SETTINGS
---------------------------

Important effective settings from config.parse-1.profile.json:

- runtime.job_name = parse-1
- runtime.worker_count = 8
- runtime.vimeo_authenticated_session = true
- workers.count = 8
- workers.stagger_start_seconds = 30
- workers.shared_media_dirs = true
- settings.download_only_original = true
- settings.download_interface = telegram-wg
- settings.download_retry_interface = ""
- settings.direct_download_timeout_seconds = 10
- settings.curl_stall_timeout_seconds = 60
- offload.enabled = true
- offload.storage_root = /home/msu_cc/mount/mimas/vimeo/2025scraped/parse-1
- offload.delete_local_video_after_upload = true
- offload.validate_with_ffprobe = true
- batches.stop_on_batch_error = false
- batches.max_batch_retries = 2

Meaning:

- page/API/login flow is normal browser/API work
- file download itself is forced through telegram-wg immediately
- there is no direct-first media attempt for parse-1
- curl may keep running while data arrives normally
- if curl speed drops below 1 byte/sec for 60 seconds, curl fails
- partial downloads are resumable because resume_partial_downloads = true
- one failed batch does not stop the whole queue
- a failed batch is re-queued automatically up to 2 times

5. WHAT HAPPENS TO EACH VIDEO
-----------------------------

For every Vimeo URL:

1. video_id is extracted
2. Vimeo API is queried
3. if download is impossible, the URL is not downloaded
4. if the page must be checked, SeleniumBase opens the Vimeo page
5. if auth is required, worker logs in with the configured Vimeo account
6. worker opens the Download menu and collects download options
7. because download_only_original = true:
   - if Original exists, it is downloaded
   - if download exists but Original does not exist, a compact JSON is saved to videos/not_downloaded
   - if there is no usable link, the URL is added to workers/no_links_urls.txt
8. downloaded videos are then picked up by offload watcher
9. watcher copies media + metadata to mimas
10. watcher verifies the media with ffprobe
11. watcher updates offload_registry.json and _offload metadata
12. watcher deletes the local media file if upload was verified

8. HOW TO READ assignment_state.json
------------------------------------

Each batch has a state item:

- pending
- running
- completed
- failed

Meaning:

- pending: batch was not started yet
- pending: also used when a running batch was re-queued for retry
- running: batch is currently assigned to one active worker slot
- completed: batch finished and summary/results were collected
- failed: batch process exited badly, exhausted retries, or required output files were missing

This file is the main truth source for queue progress.

Useful fields in each batch item:

- assigned_worker
- retry_count
- exit_code
- last_error

10. HOW OFFLOAD RESTART WORKS
-----------------------------

Offload watcher is restart-safe.

It uses:

- offload_registry.json
- _offload field inside local downloaded metadata JSON

If a video was already uploaded and remote file still exists:

- watcher does not upload it again
- if local media still exists and delete-local-video is enabled, watcher may delete it

If local media is already deleted but metadata says uploaded:

- watcher does not re-upload

If remote file is missing but local media still exists:

- watcher can upload again

Important:

- do not delete offload_registry.json during an active production run
- do not delete downloaded metadata JSON during an active production run


11. HOW TO RESTART AFTER INTERRUPTION
-------------------------------------

If parser stops unexpectedly:

1. keep output/runs/parse-1 intact
2. restart parser with the same command
3. restart offload watcher with the same command

Why this works:

- assignment_state.json resets stale running batches back to pending
- each batch has its own resume_state.json
- partial downloads can resume
- already uploaded files are tracked by offload_registry.json
- re-queued batches keep their retry_count

If you updated code or config:

1. stop parser and watcher
2. keep output/runs/parse-1 intact
3. start parser with the same command
4. start watcher with the same command

If an older run left permanent failed batches that you want to retry once with the
new logic, edit assignment_state.json and switch those batch items from failed to
pending before restart.

13. COMMON FAILURE CASES
------------------------

A. Batch fails immediately with missing summary/results

What it usually means:

- batch worker died before finishing setup
- source_json path in manifest was wrong
- config/secrets loading failed

Where to look:

- workers/coordinator.log
- shards/batch_0001/download.log


B. Login appears incomplete

What it means:

- Vimeo login flow did not complete
- account challenge or page timing issue
- batch will be re-queued automatically until max_batch_retries is exhausted
- other running batches keep working because stop_on_batch_error = false

Where to look:

- grep login errors in shard logs
- check login_failure_attempt_*.html if present in batch dir


C. No downloads happen, only Original detection

What it usually means:

- download path is broken
- wrong interface
- curl cannot use the requested WG interface

Where to look:

- grep "via curl on interface telegram-wg"
- grep "Successfully downloaded"
- inspect the current batch download.log


D. Offload fails with ffprobe

What it means:

- ffprobe is missing or media validation failed

Checks:

  command -v ffprobe
  ffprobe -version | head


E. Offload does not upload anything

Possible reasons:

- parser has not finished any video yet
- only .part files exist
- local media file is too new for min_file_age_seconds
- storage_root is wrong

Where to look:

- offload.log
- videos/downloaded/<id>/
